# 经典问题

## volatile是否可以修饰const

可以。`volatile const` 是合法且常见的组合，用于描述**只读但可能被外部因素修改**的变量。

### 各自语义

| 关键字 | 作用 |
|--------|------|
| `const` | 程序不能通过常规赋值修改该变量 |
| `volatile` | 变量可能被程序控制流之外的因素（硬件、中断、其他线程）修改 |

### 典型场景：只读硬件寄存器

```c
// 只读状态寄存器：硬件可改，程序只读
volatile const uint32_t * const status_reg = (volatile const uint32_t *)0x40021000;

// 读取最新状态（每次从内存读取，不优化）
uint32_t status = *status_reg;
```

### 解析

```c
volatile const uint32_t * const reg;
//     ^^^^^^   ^^^^^^
//     值可变   值不可改（程序视角）
//              ^^^^^^^^^^
//              指针本身也不可改
```

- 第一个 `const`：指向的内容是常量（程序不能写）
- `volatile`：但硬件可能修改这个"常量"
- 第二个 `const`：指针本身也是常量（固定指向该寄存器）

## 如何快速操作硬件寄存器

通过内存映射指针直接访问寄存器地址。

### 基本写法

```c
#define REG_ADDR 0x40021000

// 写寄存器
*(volatile uint32_t *)REG_ADDR = 0x1;

// 读寄存器
uint32_t val = *(volatile uint32_t *)REG_ADDR;

// 位操作（置位/清零）
*(volatile uint32_t *)REG_ADDR |=  (1 << 3);  // 置位bit3
*(volatile uint32_t *)REG_ADDR &= ~(1 << 3);  // 清零bit3
```

### 封装宏（推荐）

```c
#define REG32(addr) (*(volatile uint32_t *)(addr))
#define REG16(addr) (*(volatile uint16_t *)(addr))
#define REG8(addr)  (*(volatile uint8_t  *)(addr))

// 使用
REG32(0x40021000) = 0x1;
uint32_t status = REG32(0x40021004);
REG32(0x40021000) |= (1 << 3);
```

### 为什么必须加volatile

| 不加volatile | 加volatile |
|-------------|-----------|
| 编译器可能优化掉重复读写 | 每次访问都实际读写内存 |
| 可能使用缓存的旧值 | 获取硬件最新状态 |
| 写入可能被优化掉 | 确保写入生效 |

### 注意事项

- **权限**：用户空间需通过 `/dev/mem` 或 `mmap`，内核空间可直接访问
- **类型匹配**：32位寄存器用 `uint32_t*`，16位用 `uint16_t*`
- **字节序**：注意大小端对多字节寄存器的影响

## 如何快速比较两组寄存器的位差异

使用**按位异或（XOR）** + **popcount** 统计不同位数。

### 原理

```
regA: 1100 1100
regB: 1010 1010
XOR:  0110 0110  <- 1表示该位不同
popcount = 4     <- 共4位不同
```

### 实现

```c
#include <stdint.h>

// 方法1：内置函数（最快，CPU指令）
#ifdef __GNUC__
    #define POPCOUNT(x) __builtin_popcount(x)
#else
    // 软件实现
    static inline int popcount(uint32_t x) {
        x = (x & 0x55555555) + ((x >> 1) & 0x55555555);
        x = (x & 0x33333333) + ((x >> 2) & 0x33333333);
        x = (x & 0x0F0F0F0F) + ((x >> 4) & 0x0F0F0F0F);
        x = (x & 0x00FF00FF) + ((x >> 8) & 0x00FF00FF);
        x = (x & 0x0000FFFF) + ((x >> 16) & 0x0000FFFF);
        return x;
    }
    #define POPCOUNT(x) popcount(x)
#endif

// 计算差异位数
int count_different_bits(uint32_t a, uint32_t b) {
    return POPCOUNT(a ^ b);
}

// 获取具体哪些位不同（位掩码）
uint32_t get_diff_mask(uint32_t a, uint32_t b) {
    return a ^ b;  // 1表示不同的位
}
```

### 性能对比

| 方法 | 时间复杂度 | 说明 |
|------|-----------|------|
| 逐位检查 | O(n) | n为位数，32次循环 |
| 查表法 | O(1) | 256字节查找表 |
| **内置popcount** | **O(1)** | **单条CPU指令，推荐** |

## 堆和栈的区别

### 核心对比

| 特性 | 栈（Stack） | 堆（Heap） |
|------|-------------|------------|
| **管理方式** | 编译器自动分配/释放 | 程序员手动分配/释放（`malloc`/`free`） |
| **存储内容** | 函数参数、局部变量、返回地址 | 动态分配的数据（运行时确定大小） |
| **空间大小** | 较小（通常1-8MB） | 较大（受系统可用内存限制） |
| **生长方向** | 高地址 → 低地址 | 低地址 → 高地址 |
| **分配速度** | 快（仅移动栈指针） | 慢（需查找合适内存块） |
| **碎片问题** | 无 | 可能产生碎片 |
| **线程安全** | 每个线程独立栈 | 需同步机制保护 |

### 内存不free的后果

| 问题 | 说明 |
|------|------|
| **内存泄漏** | 持续申请不释放，最终耗尽内存导致程序崩溃 |
| **内存碎片** | 频繁分配/释放导致碎片，大内存申请失败 |
| **资源浪费** | 占用内存无法被其他模块使用 |
| **性能下降** | 内存管理开销增加，系统变慢 |

> **最佳实践**：`free` 后立即将指针置 `NULL`，防止悬空指针。

## 堆和栈的分配方式对比

| 对比项 | 堆（Heap） | 栈（Stack） |
|--------|-----------|-------------|
| **分配方式** | 手动（`malloc`/`new`） | 自动（编译器管理） |
| **释放方式** | 手动（`free`/`delete`） | 函数返回时自动释放 |
| **分配速度** | 慢（需查找内存块） | 快（移动栈指针） |
| **空间大小** | 大（系统可用内存） | 小（固定，通常1-8MB） |
| **内存访问** | 全局可访问，可共享 | 作用域内访问 |
| **碎片问题** | 可能产生碎片 | 无碎片 |
| **生命周期** | 由程序员控制 | 随函数调用结束 |

## 为什么栈的访问速度比堆快

| 原因 | 说明 |
|------|------|
| **分配方式** | 栈仅需移动栈指针（O(1)）；堆需查找合适内存块，可能触发系统调用 |
| **缓存局部性** | 栈数据物理连续，CPU缓存命中率高；堆数据分散，缓存不友好 |
| **编译器优化** | 栈大小编译期确定，编译器可精确优化；堆大小运行时确定，优化受限 |
| **无锁分配** | 栈分配无需同步；堆在多线程下需加锁保护 |
| **无碎片** | 栈连续分配无碎片；堆碎片导致分配效率下降 |

## 如何用C语言判断和转换大小端

### 判断大小端

```c
#include <stdint.h>
#include <stdbool.h>

// 方法1：联合体（最直观）
bool is_little_endian(void) {
    union {
        uint32_t val;
        uint8_t bytes[4];
    } u = { .val = 1 };
    return u.bytes[0] == 1;  // 小端：低字节在低地址
}

// 方法2：指针强制转换（更简洁）
bool is_little_endian2(void) {
    uint32_t val = 1;
    return *(uint8_t *)&val == 1;
}
```

### 大小端转换

```c
// 16位交换
static inline uint16_t swap16(uint16_t x) {
    return (x << 8) | (x >> 8);
}

// 32位交换
static inline uint32_t swap32(uint32_t x) {
    return ((x << 24) & 0xFF000000) |
           ((x << 8)  & 0x00FF0000) |
           ((x >> 8)  & 0x0000FF00) |
           ((x >> 24) & 0x000000FF);
}

// 使用内置函数（GCC/Clang）
#define bswap16(x) __builtin_bswap16(x)
#define bswap32(x) __builtin_bswap32(x)
#define bswap64(x) __builtin_bswap64(x)
```

### 网络字节序转换

```c
#include <arpa/inet.h>  // Linux

uint32_t htonl(uint32_t hostlong);   // 主机→网络（大端）
uint16_t htons(uint16_t hostshort);  // 主机→网络（大端）
uint32_t ntohl(uint32_t netlong);    // 网络→主机
uint16_t ntohs(uint16_t netshort);   // 网络→主机
```

## 指针访问栈地址与堆地址的速度对比

**结论**：访问栈地址通常比堆地址更快。

| 因素 | 栈 | 堆 |
|------|-----|-----|
| **内存连续性** | 物理连续，缓存友好 | 可能分散，缓存不友好 |
| **分配开销** | 仅移动栈指针 | 需查找空闲块，可能触发系统调用 |
| **寄存器支持** | 有专用栈指针寄存器 | 无专用寄存器 |
| **缺页中断** | 启动时已映射 | 首次访问可能触发缺页 |
| **多线程** | 每个线程独立栈，无竞争 | 需加锁保护，存在竞争 |

### 缓存局部性（Cache Locality）

**栈的缓存友好性**：

-   栈内存通常位于CPU缓存的热点区域，因其连续性和高频访问特性，数据更易被缓存命中。
-   函数调用的局部变量和参数集中在栈帧中，缓存预取（Prefetching）效率高。

**堆的缓存问题**：

-   堆内存分散性导致缓存利用率低，频繁访问不同堆块可能触发缓存行替换，增加延迟。
-   大块堆内存（如动态数组）可能跨多个缓存行，按行访问时仍需处理缓存未命中。

### 总结与建议

| 特性         | 栈地址访问                 | 堆地址访问               |
| ------------ | -------------------------- | ------------------------ |
| **速度**     | 更快（硬件优化、缓存友好） | 较慢（动态管理、碎片化） |
| **适用场景** | 局部变量、短生命周期数据   | 动态数据结构、跨函数数据 |

编程建议：

-   优先使用栈存储高频访问的小数据（如循环变量、函数参数）。
-   堆适合存储大对象或需灵活管理的数据（如链表、动态数组），但需注意性能损耗和内存管理。

## do{}while(0)的使用场景

`do { } while (0)` 是宏定义多语句的标准技巧，确保宏在任何上下文都能正确工作。

### 核心作用

| 场景 | 说明 |
|------|------|
| **多语句宏** | 包裹多条语句，避免语法错误 |
| **局部变量** | 宏内可使用局部变量，不污染外部 |
| **break控制** | 可用break提前退出宏内逻辑 |

### 对比示例

```c
// 错误写法：if分支只包含第一条语句
#define SAFE_FREE(p) free(p); p = NULL;

if (cond)
    SAFE_FREE(ptr);  // 展开后：if(cond) free(ptr); p = NULL;  // p=NULL总在if外！
else
    ...

// 正确写法：do-while(0)确保宏作为单条语句
#define SAFE_FREE(p) do { \
    free(p); \
    (p) = NULL; \
} while (0)

if (cond)
    SAFE_FREE(ptr);  // 展开为单条语句，正确
else
    ...
```

### 完整示例

```c
#define HANDLE_ERROR(err, msg) do { \
    if ((err) < 0) { \
        fprintf(stderr, "Error %d: %s\n", (err), (msg)); \
        goto cleanup; \
    } \
} while (0)

// 使用
int fd = open("file", O_RDONLY);
HANDLE_ERROR(fd, "open failed");
```

## delay和sleep的区别

| 特性 | delay | sleep |
|------|-------|-------|
| **功能** | 产生精确时间延迟 | 让线程/进程休眠，释放CPU |
| **CPU占用** | **忙等待**，占用CPU（除非用硬件定时器） | **阻塞**，不占用CPU |
| **精度** | 高（微秒/毫秒级） | 低（受调度器影响，通常10ms级） |
| **应用场景** | 嵌入式硬件时序控制（LED、SPI时序等） | 多任务调度、资源等待 |
| **实现方式** | 循环计数 / 硬件定时器 | 系统调用，进入阻塞态 |

### 代码对比

```c
// delay - 忙等待（嵌入式裸机）
void delay_ms(uint32_t ms) {
    uint32_t start = get_tick();
    while (get_tick() - start < ms);  // 空转消耗CPU
}

// sleep - 阻塞（Linux/RTOS）
void task(void) {
    while (1) {
        do_work();
        sleep(1);  // 1秒内CPU可执行其他任务
    }
}
```

### 选择建议

| 场景 | 推荐 |
|------|------|
| 裸机/无OS嵌入式 | `delay` + 硬件定时器 |
| 有OS的多任务系统 | `sleep`/`usleep` |
| 需要纳秒级精度 | 硬件定时器 + 中断 |
| 需要微秒级精度 | `usleep` 或忙等待 |
| 秒级以上等待 | 绝对用`sleep`，避免浪费CPU |

## 如何合理高效地进行静态内存分配

静态分配在编译期确定内存大小和位置，避免运行时开销，适合嵌入式等资源受限场景。

### 核心原则

| 原则 | 说明 |
|------|------|
| **编译期确定** | 所有大小在编译时可知，无运行时分配开销 |
| **确定性布局** | 内存地址固定，便于硬件直接访问 |
| **无碎片** | 连续分配，不存在碎片问题 |
| **零泄漏风险** | 无需释放，生命周期与程序一致 |

### 实现方式

```c
#include <stdint.h>

#define MAX_ITEMS 100
#define NAME_LEN  50

// 静态分配全局数组
typedef struct {
    uint8_t id;
    char name[NAME_LEN];
} Item;

static Item inventory[MAX_ITEMS];  // BSS段（未初始化）
static uint32_t item_count = 0;    // Data段（已初始化）

// 静态分配在函数内（生命周期全局，作用域局部）
void counter(void) {
    static uint32_t call_count = 0;  // 只初始化一次
    call_count++;
}
```

### 优化策略

| 策略 | 说明 |
|------|------|
| **精确类型** | 用 `uint8_t` 代替 `int` 表示0-255，减少内存占用 |
| **对齐优化** | 结构体成员按大小降序排列，减少填充字节 |
| **分区管理** | 将不同功能数据分区放置，提高缓存命中率 |
| **常量替代** | 用 `const` 修饰只读数据，可能放入Flash节省RAM |
| **预留扩展** | 数组适当预留空间，避免频繁修改定义 |

### 结构体对齐优化示例

```c
// 差：需要填充字节
struct Bad {
    char a;      // 1字节 + 3填充
    uint32_t b;  // 4字节
    char c;      // 1字节 + 3填充
};  // 总大小：12字节

// 好：减少填充
struct Good {
    uint32_t b;  // 4字节
    char a;      // 1字节
    char c;      // 1字节
    // 2字节填充（不可避免）
};  // 总大小：8字节
```

## 正常重启时是否需要释放内存

**不需要手动释放**。

正常重启（软件复位、看门狗复位、系统重启）时，整个进程地址空间被销毁，操作系统会回收所有资源。手动释放内存是**多余操作**，反而增加重启时间。

### 不同场景

| 重启类型 | 内存处理 | 说明 |
|----------|----------|------|
| **进程退出** | OS自动回收所有内存 | `main()`返回或调用`exit()` |
| **系统重启** | 内核重新初始化 | 内存管理器重置 |
| **看门狗复位** | 硬件复位，内存清零 | 所有状态丢失 |
| **RTOS任务重启** | 任务栈重新分配 | 静态任务栈不变 |

### 但需注意

```c
// 1. 持久化数据必须提前保存
void reboot_system(void) {
    save_config_to_flash();   // 先保存配置
    save_logs();              // 保存日志
    // 无需free任何内存
    system_reset();           // 直接复位
}

// 2. 共享资源需优雅关闭
void graceful_shutdown(void) {
    close_all_fds();          // 关闭文件描述符
    flush_disk_cache();       // 刷盘
    // 网络连接由OS清理
}
```

-   内存管理：大多数现代操作系统在启动时会重新初始化其内存管理子系统，包括清除和重新分配内存。在这个过程中，之前申请的动态内存会被标记为未使用，并可以被新的进程或线程重新利用。
-   资源回收：当操作系统重启时，它会关闭所有正在运行的程序并释放它们所占用的资源，包括打开的文件、网络连接等。这有助于防止资源泄漏和保持系统稳定性。
-   数据一致性：在某些情况下，应用程序可能存在未保存的数据或状态。重启时，这些数据应该适当地处理，以确保数据一致性。例如，有些应用程序可能需要在退出前保存其状态或设置。

需要注意的事项

-   应用程序行为：对于特定的应用程序，如果它们没有正确地处理资源释放（如没有实现析构函数或者清理代码），那么在正常重启后这些资源仍然可能没有被释放。因此，设计良好的应用程序应确保在停止时能够妥善管理其使用的资源。
-   临时文件与缓存：如果你的应用使用了临时文件或缓存，这些也应该在重启过程中得到妥善处理。尽量避免不必要的数据保留，以免影响下次启动时的性能。
-   整体设计考虑：虽然操作系统会自动处理很多内存和资源管理，但对于特定类型的嵌入式系统或者特殊环境（例如实时操作系统），开发者可能需要自行编写代码以确保彻底释放某些关键资源，以避免潜在的问题。

## 掉电关机时是否需要释放内存

**不需要，也做不到**。

掉电时CPU停止工作，操作系统没有机会执行任何清理代码。此时关注点是**数据持久化**，而非内存释放。

### 掉电风险

| 风险 | 说明 | 防护 |
|------|------|------|
| **数据丢失** | 内存中未保存数据丢失 | 关键数据定期写入Flash/EEPROM |
| **文件系统损坏** | 正在写入的文件不完整 | 使用日志型文件系统（JFFS2/EXT4） |
| **配置丢失** | 运行时参数未持久化 | 配置变更立即写非易失存储 |

### 防护措施

```c
// 1. 关键数据双备份写Flash
void save_critical_data(const Config *cfg) {
    flash_erase(CONFIG_SECTOR_B);
    flash_write(CONFIG_SECTOR_B, cfg, sizeof(Config));

    if (verify_config(CONFIG_SECTOR_B)) {
        flash_erase(CONFIG_SECTOR_A);
        flash_write(CONFIG_SECTOR_A, cfg, sizeof(Config));
    }
}

// 2. 电源异常中断（需硬件支持）
void power_fail_isr(void) {
    // UPS/大电容供电，只有几ms时间
    save_critical_data(&g_config);  // 快速保存
    set_power_down_flag();           // 标记正常关机
}
```

## 非掉电异常的处理方法

非掉电异常（段错误、断言失败、看门狗超时）需要分层处理，确保系统可恢复。

### 分层处理策略

| 层级 | 机制 | 作用 |
|------|------|------|
| **预防** | 静态分析、单元测试 | 在编码阶段发现问题 |
| **捕获** | 信号处理、try-catch | 运行时捕获异常 |
| **恢复** | 看门狗复位、检查点 | 系统自动恢复 |
| **诊断** | 日志、Core Dump | 事后分析问题 |

### C语言异常捕获

```c
#include <signal.h>
#include <setjmp.h>

static jmp_buf g_recovery_point;

void signal_handler(int sig) {
    log_error("Signal %d caught", sig);
    longjmp(g_recovery_point, sig);  // 跳转到恢复点
}

void critical_task(void) {
    signal(SIGSEGV, signal_handler);
    signal(SIGBUS, signal_handler);

    if (setjmp(g_recovery_point) == 0) {
        // 正常执行
        risky_operation();
    } else {
        // 异常恢复
        log_error("Task failed, entering safe mode");
        enter_safe_mode();
    }
}
```

### 检查点机制

```c
typedef struct {
    uint32_t state;
    uint32_t progress;
    uint8_t  buffer[256];
} Checkpoint;

void do_long_task(void) {
    Checkpoint cp;

    for (int i = 0; i < 100; i++) {
        process_step(i);

        // 每10步保存检查点
        if (i % 10 == 0) {
            cp.state = STATE_RUNNING;
            cp.progress = i;
            memcpy(cp.buffer, get_data(), sizeof(cp.buffer));
            save_checkpoint(&cp);
        }
    }
}
```

## 非正常掉电的保护机制

### 硬件保护

| 措施 | 原理 | 适用场景 |
|------|------|----------|
| **UPS** | 电池逆变供电，提供数分钟关机时间 | 服务器、关键设备 |
| **超级电容** | 大容量电容储能，提供数秒保存时间 | 嵌入式设备 |
| **硬件看门狗** | 超时自动复位，防止死机 | 所有嵌入式系统 |
| **掉电检测中断** | 电源跌落前触发中断，紧急保存 | 有硬件支持的系统 |

### 软件保护

```c
// 掉电检测ISR（需硬件支持电源监控）
void power_fail_isr(void) {
    // 关闭非必要外设，降低功耗
    disable_peripherals();

    // 快速保存关键数据（只有几ms时间）
    g_config.power_down_flag = POWER_DOWN_UNEXPECTED;
    flash_write(CONFIG_ADDR, &g_config, sizeof(Config));

    // 设置标志，下次启动知道是异常掉电
    set_boot_reason(BOOT_REASON_POWER_FAIL);
}

// 启动时检查
void system_init(void) {
    BootReason reason = get_boot_reason();

    if (reason == BOOT_REASON_POWER_FAIL) {
        // 检查数据完整性
        if (!verify_config()) {
            restore_default_config();
        }
        // 检查文件系统
        fsck_check();
    }
}
```

### 数据完整性保障

| 方法 | 说明 |
|------|------|
| **双备份** | 数据写A区，验证后写B区 |
| **CRC校验** | 每个数据块附带CRC32校验 |
| **原子写** | 使用标志位确保写入完整性 |
| **日志型文件系统** | JFFS2/YAFFS/EXT4日志模式 |

**系统检查点机制**：建立系统检查点是一种有效的保护方法。在系统运行过程中，定期设置检查点，将系统的关键状态（包括内存数据、进程状态、设备状态等）保存到非易失性存储介质中。当发生掉电后，系统可以从最近的检查点恢复。这种机制类似于游戏中的存档功能，通过合理设置检查点的间隔和内容，可以在保证系统性能的前提下，最大程度地减少掉电造成的损失。在实现检查点机制时，需要考虑数据的一致性和完整性，避免在保存检查点数据的过程中出现新的问题。

## 如何确定程序运行所需的堆栈大小

### 计算方法

```
总栈大小 = 最大调用链深度 × 平均栈帧大小 + 中断/异常栈 + 安全余量
```

### 静态分析

```c
// 1. 统计各函数栈帧
void func_a(void) {
    char buf[1024];      // 1KB
    int x;               // 4B
    // 栈帧 ≈ 1024 + 4 + 保存寄存器(约32B) + 返回地址(8B) ≈ 1.1KB
}

void func_b(void) {
    double matrix[100];  // 800B
    func_a();            // 调用链叠加
    // 栈帧 ≈ 800 + 1100 ≈ 1.9KB
}

// 2. 递归函数
int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);  // 深度n，总栈 = n × 单帧大小
}
```

### 动态测量工具

| 工具/方法 | 说明 |
|-----------|------|
| **GCC `-fstack-usage`** | 编译时生成 `.su` 文件，记录每个函数栈使用量 |
| **Valgrind** | `massif` 工具分析堆栈峰值 |
| **静态分析工具** | PC-lint, Coverity 可估算最大栈深 |
| **运行时水印** | 初始化时填充栈空间，检查最大使用位置 |

### 运行时水印法

```c
#define STACK_SIZE 0x10000  // 64KB栈

void stack_init(void) {
    // 填充特定模式
    memset(stack_bottom, 0xA5, STACK_SIZE);
}

size_t stack_max_usage(void) {
    uint8_t *p = stack_bottom;
    while (*p == 0xA5) p++;
    return STACK_SIZE - (p - stack_bottom);
}
```

### 安全建议

| 场景 | 建议栈大小 |
|------|-----------|
| 裸机中断 | ≥ 1KB |
| RTOS任务 | ≥ 2-4KB |
| Linux线程 | ≥ 8KB（默认8MB可调整） |
| 递归算法 | 按递归深度预留 |
| 安全余量 | 实际测量的 1.5-2 倍 |

## 多线程环境下野指针的风险

### 典型场景：Use-After-Free

```c
int *shared_ptr = malloc(sizeof(int));
*shared_ptr = 10;

// 线程1：释放内存
void thread1(void) {
    free(shared_ptr);
    shared_ptr = NULL;  // 即使置空也有竞态窗口
}

// 线程2：访问内存
void thread2(void) {
    if (shared_ptr != NULL) {  // 检查通过但可能已被释放
        *shared_ptr = 20;      // Use-After-Free！未定义行为
    }
}
```

### 风险后果

| 风险 | 说明 |
|------|------|
| **数据损坏** | 写入已释放内存，破坏堆管理结构 |
| **信息泄露** | 读取已释放内存，获取敏感数据 |
| **程序崩溃** | 触发段错误（SIGSEGV） |
| **代码执行** | 攻击者控制释放后重新分配的内存内容 |

### 解决方案

```c
// 方案1：互斥锁保护
static pthread_mutex_t ptr_mutex = PTHREAD_MUTEX_INITIALIZER;

void safe_free(void **pp) {
    pthread_mutex_lock(&ptr_mutex);
    free(*pp);
    *pp = NULL;
    pthread_mutex_unlock(&ptr_mutex);
}

// 方案2：原子指针（C11）
#include <stdatomic.h>

_Atomic(int*) atomic_ptr;

void safe_access(void) {
    int *p = atomic_load(&atomic_ptr);
    if (p != NULL) {
        // 但仍需小心：加载后可能被其他线程释放
    }
}

// 方案3：引用计数（最可靠）
typedef struct {
    int ref_count;
    void *data;
} RefCounted;

void ref_counted_free(RefCounted *rc) {
    if (__sync_sub_and_fetch(&rc->ref_count, 1) == 0) {
        free(rc->data);
        free(rc);
    }
}
```
